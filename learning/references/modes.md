# 模式专用工作流

只阅读当前模式的部分。共享评分、节奏、提示规则以 SKILL.md 为准。

## 技术与工程实践

不要停留在“是什么”。问题围绕：为什么需要、不用会怎样、与另一方法的区别、什么时候不用、故障怎么定位、规模扩大十倍、前提失效。让用户先选择方案，再解释原因与取舍。

实践任务给背景、约束、输入/输出和 2～4 条验收标准，先等用户方案或实现。优先沿用用户语言和真实工程上下文，无上下文时选最小可运行示例。不引入生产操作。

- 编码：用户先写核心函数，测试正常、错误与边界路径；提示后通过标记 assisted，另题闭卷验证。
- Debug/日志：先给症状与必要证据，用户提出假设、验证步骤和修复；区分定位证据和猜测。
- API/数据库：用户先设计接口、表结构与状态变化，测试幂等、并发、事务、索引与失败恢复。
- 系统设计：用户先画请求链、状态归属和约束，再注入故障或十倍负载；不能仅列技术名词。
- 性能分析：先建立可测假设和基线；未执行的指标不写成结果。

实践迁移改变问题的关键条件，不只改变量名。例：缓存失效时的并发请求 → 回源依赖改成限流严格、收费的第三方 API。请用户设计请求合并范围、等待/超时、失败处理与新鲜度取舍；答题前不提供这些问题的解法。

## Question Driven Source Reading

禁止默认逐行讲解仓库。开卷定位与闭卷重建分开计分。

1. 先提 3～7 个本次关键问题，例如：请求从哪里进入？状态在哪里保存？tool call 在哪里执行？retry 在哪里？streaming event 如何传播？
2. 用户先预测或说明已知调用链；不知道可直说，再开始定位。使用 `rg` 查入口、实际 composition root 和运行时装配。
3. 从入口追核心调用链。确认该路径确实被调用，不能根据文件名或 README 推定能力。
4. 查关键状态：谁创建、谁持有、如何更新、何时释放、如何隔离。
5. 查异常路径：超时、取消、重试、失败事件、资源回收、重复执行。
6. 查边界：并发、幂等、streaming、跨进程/持久化；按主题选相关项，不一律审计所有问题。
7. 让用户离开资料重建流程：输入 → 调用 → 状态变化 → 输出/事件 → 异常出口。以具体文件、符号、行号或 commit 校核。
8. Application：让用户定位一个行为或提出最小修改并给验证办法；Transfer：改变装配、并发或失败条件，让用户推断影响并定位验证点。

仅收集必要片段。记录路径与 commit、关键边界和评估结论，不保存整份私有源码。读不到文件时明确限制。

## 论文

获取全文或用户提供的原文；只有摘要时只对摘要可支持部分提问，实验、复现与结果标为待验证。先让用户从标题/摘要尝试判断问题与可能方法，再给必要阅读引导，不一开始逐段总结。

按十个维度组织理解，选 3～7 个核心知识点训练，不把十个维度都一次变成十道题：

| 维度 | 要定位的证据 |
|---|---|
| Research Question | 哪个可测问题、什么输入输出与假设 |
| Motivation | 为什么这个问题值得解决 |
| Existing Limitation | 现有方法在哪些条件下失效 |
| Core Idea | 核心机制、相对基线的新贡献 |
| Method | 模块、算法、目标函数、关键依赖 |
| Experiment | 数据、基线、消融、评估协议与指标 |
| Result | 结果支持哪项 claim，效果范围和不确定性 |
| Limitation | 适用边界、成本、外部有效性、可能混淆变量 |
| Reproduction | 最小复现、资源、第一步、成功标准 |
| Transfer | 换数据、任务或假设是否仍有效 |

闭卷问题从以下挑少量：论文解决什么问题？为什么原方法不行？真正贡献是什么？最关键实验是什么？哪项实验能证明核心 claim？有哪些 confounder？复现第一步做什么？

证据判断：相关性结果不等于机制证明；区分论文自述与实际支持。用户先提出证明/证伪核心 claim 的实验，再对照文中设计。

实践可以是推导小例子、实现核心机制、设计消融、最小复现计划。没有条件跑实验时明确“设计评估通过”，不能说“复现成功”；Level 4 至少要求独立可验收应用和新场景迁移，必要时保留未验证执行能力。

## AI / Agent

Agent、RAG、Tool Calling、Memory、Evaluation、Tracing、Multi-Agent、LLM Backend，优先真实系统设计 + 最小实现 + failure case。用户不必先背框架术语。

示例任务按目标选用，不一次全部展开：

- RAG：带版本变化的知识库问答。用户设计检索、上下文构建和评估；迁移到权限隔离、召回下降或错误引用场景。
- Memory：conversation memory、user profile、task memory、tool history 同时存在。用户定义所有权、隔离、检索、TTL、更新冲突和生命周期；迁移到任务重启、跨用户污染或删除请求。
- Tool Calling：用户先实现校验、执行与结果回传；迁移到超时后结果不确定、重复调用或流式参数未完整。
- Evaluation / Tracing：用户把质量下降拆成检索、工具、决策与生成故障，给指标与可追踪证据；迁移到离线分数上升但线上失败。
- Multi-Agent：用户先判断是否需要多个 Agent，给状态边界与通信协议；迁移到重复执行、消息乱序或共享状态冲突。
- LLM Backend：用户设计限流、预算、超时、流式事件、重试与幂等；迁移到 provider 切换或部分成功。

验收关注可观察行为、故障恢复和 tradeoff。不要将助手代写或假跑的 Demo 当成用户能力。
